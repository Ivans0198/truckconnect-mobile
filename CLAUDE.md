# CLAUDE.md: TruckConnect Driver (mobile)

## Project

Mobile app for TruckConnect's drivers (Melbourne metro): today's orders,
the active run with background GPS, POD capture, HVNL fatigue, compliance
documents, notifications and incident reports. **The UI is in English.**

The backend already exists. Read these before touching a screen:

| Document                                      | What it is                                                         |
| --------------------------------------------- | ------------------------------------------------------------------ |
| `docs/openapi.json`                           | **The API contract, source of truth.** Not in it = does not exist. |
| `docs/CLAUDE_MOBILE.md`                       | Product, the 5 critical rules, endpoints, screen → mockup map      |
| `docs/PROMPT_MOBILE.md`                       | What each screen does                                              |
| `docs/driver-incidents-mobile-requirement.md` | The three Incidents screens (no mockup)                            |
| `docs/mockups/`                               | HTML mockups + PNG of each phone frame (ui-reviewer Mode A)        |
| `design-system.md`                            | Tokens and visual rules; in code, `src/theme/tokens.ts`            |

Stack: Expo SDK 58 in managed mode, always on a development build (never
Expo Go). React Native 0.88, TypeScript strict, Expo Router and TanStack
Query. The API client is `openapi-fetch` with types generated by
`pnpm gen:api`; never hand-write an API type. Tests use jest-expo with
Testing Library and msw, Playwright on Expo web, and Maestro on Android. pnpm
with `nodeLinker: hoisted`. The stack profile is
`.factory/rules/stacks/expo-rn.md` (`factory.json` → `stack`).

## Testing layers

| Layer                               | Command            | Runs in                | Catches                                                                 |
| ----------------------------------- | ------------------ | ---------------------- | ----------------------------------------------------------------------- |
| jest + Testing Library + msw        | `pnpm test`        | Stop gate, CI          | Logic, states, the contract                                             |
| Playwright + axe on Expo web        | `pnpm e2e`         | Stop gate, CI          | Layout vs. mockup, accessibility                                        |
| **Maestro on the Android emulator** | `pnpm e2e:android` | **a person's machine** | **Native behavior**: dev build boots, permissions, camera, GPS, offline |

- **msw in jest:** handlers go through `src/test/server.ts`; any request
  without a handler fails the test. Jest runs on Node's fetch, restored by
  `tests/jest/environment.js`; the app on the phone uses `expo/fetch`.
- **Expo web is an approximation of Android, not Android.** Screens that use
  a native-only module (camera, location, signature) need a web stub so
  Playwright and the ui-reviewer can still render them.
- **Maestro is outside the gate on purpose**: it needs an emulator with the
  development build installed, which neither CI nor the dev container has.
  A story that touches something native (POD, GPS, push, offline queue,
  permissions) adds its flow to `.maestro/` **and** says in the PR that a
  person must run `pnpm e2e:android` on the emulator before merging. Never
  claim a Maestro flow passed without having run it.
- Running the app on Android: `pnpm android` (`expo run:android`) builds and
  installs the development build on the running emulator or a connected
  phone. The emulator reaches the host's API at `http://10.0.2.2:<port>`, not
  `localhost`: set `EXPO_PUBLIC_API_URL` accordingly.

## Project skills

The official Expo plugin (`expo@claude-plugins-official`) is enabled for this
project. Load its skills before writing code they cover:

| Skill                     | Load it when…                                                         |
| ------------------------- | --------------------------------------------------------------------- |
| `expo:expo-overview`      | starting any Expo task: it routes to the right skill below            |
| `expo:expo-router`        | adding or changing routes, the `(auth)` / `(tabs)` groups, modals     |
| `expo:expo-data-fetching` | writing a query, a mutation, loading/error states or offline handling |
| `expo:expo-ui`            | picking a component: sheets, pickers, toggles, menus                  |
| `expo:expo-native-ui`     | building a screen's layout and native styling                         |
| `expo:expo-animation`     | adding motion, gestures, press feedback or haptics                    |
| `expo:expo-dev-client`    | changing native config that needs a new development build             |
| `expo:expo-upgrade`       | a ticket that moves to another Expo SDK                               |

**What wins when they disagree.** The Expo skills give general advice. This
project has decisions they do not know about, and those come first:

1. `docs/openapi.json` and `docs/CLAUDE_MOBILE.md` (the contract and the
   product rules).
2. The screen's mockup in `docs/mockups/` and `design-system.md`. A skill's
   platform styling (SF Symbols, iOS semantic colors, native look) never
   overrides the mockup.
3. The stack profile, `.factory/rules/stacks/expo-rn.md`.
4. The Expo skills.

A skill that suggests a new dependency still needs the one-line
justification in the PR, and is installed with `pnpm exec expo install`.
